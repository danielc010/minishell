MINISHELL — PROJECT PLAN & SCHEDULE (2-PERSON SPLIT)
=====================================================

ARCHITECTURE OVERVIEW
---------------------
Input (readline) -> Lexer -> Parser -> Expander -> Executor
                   [-------- PERSON A ---------]   [-- B --]

PERSON A owns: Lexer, Parser, Expander, echo/pwd/env built-ins
PERSON B owns: Executor, Pipes, Redirections, cd/export/unset/exit built-ins, Signals

SHARED / BOTH: Phase 1 foundation, data structures, testing, Makefile, README


=====================================
PHASE 1 — FOUNDATION (Days 1–3) [BOTH]
=====================================
[ ] Project structure: src/, include/, libft/
[ ] Makefile with all required rules (NAME, all, clean, fclean, re)
[ ] readline loop with prompt + add_history
[ ] Global signal variable skeleton (only 1 global allowed — just stores signal number)
[ ] Basic env copy from envp at startup

** CRITICAL: Agree on shared data structures before splitting **
   t_token  { type, value, next }
   t_redir  { type, file, fd, next }
   t_cmd    { argv[], redirs, pipe_in, pipe_out, next }

Goal: Shell boots, accepts input, exits cleanly. Structs locked in.


===========================================
PHASE 2 — LEXER / TOKENIZER (Days 4–7) [A]
===========================================
[ ] Token types: WORD, PIPE, REDIR_IN, REDIR_OUT, HEREDOC, REDIR_APPEND
[ ] Handle single quotes '...' — no interpretation inside
[ ] Handle double quotes "..." — only $ interpreted inside
[ ] Detect unclosed quotes -> print error, don't execute
[ ] Don't interpret \ or ;

Goal: Input correctly split into a token list.


======================================
PHASE 3 — PARSER (Days 8–11) [A]
======================================
[ ] Build a t_cmd list from tokens (one node per pipe segment)
[ ] Each node holds: argv[], list of redirections, pipe flags
[ ] Validate syntax (no bare |, no double redirects, etc.)

Goal: "ls -la | grep foo > out.txt" becomes a clean command structure.


======================================
PHASE 4 — EXPANDER (Days 12–13) [A]
======================================
[ ] Expand $VAR from env
[ ] Expand $? to last exit status
[ ] Strip quotes after expansion
[ ] Respect quote context (no expansion inside '...')

Goal: echo "$HOME" and echo '$HOME' behave like bash.


=========================================
PHASE 5 — EXECUTOR (Days 8–15) [B]
=========================================
(B can start this in parallel once Phase 1 structs are agreed upon)

[ ] PATH resolution for executables
[ ] fork + execve for external commands
[ ] Pipe chain: pipe(), dup2(), close unused fds
[ ] Redirections: <, >, >> via open() + dup2()
[ ] Heredoc <<: read lines until delimiter, write to temp pipe
[ ] waitpid / exit status tracking

Goal: "cat file | grep word > result" works end-to-end.


=========================================
PHASE 6 — BUILT-INS (Days 14–20) [SPLIT]
=========================================

[A] echo with -n
[A] pwd
[A] env

[B] cd (relative + absolute, update PWD/OLDPWD)
[B] export (add/update env var, print sorted if no args)
[B] unset
[B] exit (with optional status code)

Key: cd, export, unset, exit MUST run in the PARENT process (no fork).
     echo, pwd, env can run in a child (but also work in parent).


=========================================
PHASE 7 — SIGNALS (Days 20–22) [B]
=========================================
[ ] ctrl-C (SIGINT): print newline, show new prompt
[ ] ctrl-D (EOF): exit shell
[ ] ctrl-\ (SIGQUIT): do nothing in interactive mode
[ ] Different signal behaviour during child execution vs. interactive prompt

Note: Only 1 global variable allowed — must only store the signal number.
      No "norm" type structs in global scope.


==========================================
PHASE 8 — INTEGRATION & TESTING (Days 23–27) [BOTH]
==========================================
[ ] Connect A's parser output to B's executor — run full pipeline end-to-end
[ ] Valgrind — no leaks in your code (readline leaks are OK)
[ ] Edge cases: empty input, spaces only, | at start/end, nested quotes
[ ] Compare all behaviour against real bash
[ ] README: Description, Instructions, Resources + AI usage section
    (First line must be italicized: "This project has been created as part
     of the 42 curriculum by <login1>[, <login2>]")

Goal: All mandatory requirements pass cleanly.


==========================================
BONUS — (After mandatory is solid) [BOTH]
==========================================
[ ] && and || with parentheses for grouping  (touches parser + executor — do together)
[ ] * wildcard expansion in current directory (executor/expander side — B leads, A assists)

Warning: Bonus is ONLY evaluated if mandatory is 100% complete and bug-free.


KEY RULES TO REMEMBER
---------------------
- Only 1 global variable — must only store a signal number
- No norm errors — project gets 0 if norm fails (bonus files included)
- No memory leaks in your code (use valgrind regularly)
- Bash is the reference — when in doubt, test it in bash
- During evaluation a live code modification may be requested — both partners
  must understand ALL parts of the code, not just their own half
